<summary><strong>⬡ TradeSync Pro — MT5 Copy Trading Ecosystem</strong></summary>

<br/>

> **Real-time trade broadcast infrastructure built for MetaTrader 5.** Master accounts stream live trades to a central NestJS cloud server which instantly routes signals to multiple connected Slave accounts. Each Slave applies custom risk management settings and dynamic symbol mapping, enabling independent position sizing while following the Master's strategy.

<div align="center">

| Attribute | Detail |
|:---|:---|
| **Stack** | Next.js · NestJS · Python · MSSQL · MT5 API · Microservices · Modular Architecture |
| **Architecture** | API Gateway · Event-driven signal routing · CQRS-inspired module separation |
| **Scale** | Multi-account real-time trade mirroring with sub-second signal propagation |
| **Clients** | Next.js web dashboard + two Python desktop applications (Master & Slave) |
| **Security** | Role-based account isolation · Custom risk management per Slave account |
| **Impact** | Enables retail traders to copy institutional strategies with configurable risk |
| **Repository** | [github.com/awaisarif18/TradeSync_Pro](https://github.com/awaisarif18/TradeSync_Pro) |

</div>

This is my final year project and the most architecturally complex system I have built. The challenge was propagating trade signals from a live MT5 terminal through a cloud API gateway to N connected Slave accounts with latency low enough for the signals to remain actionable. The modular NestJS backend enforces strict service boundaries so each component (signal ingestion, routing, account management, risk engine) can be scaled or replaced independently. The two Python desktop clients act as MT5 bridges on the Master and Slave machines, communicating with the cloud over authenticated REST channels.

<summary><strong>⬡ LuminaFlow — High-Performance Parallel Video Engine</strong></summary>

<br/>

> **A research-grade Python video processing framework engineered to bypass the Global Interpreter Lock.** Uses a Zero-Copy Shared Memory Ring Buffer to achieve real-time parallelism for CPU-intensive computer vision workloads — without the serialisation overhead of queue-based inter-process communication.

<div align="center">

| Attribute | Detail |
|:---|:---|
| **Stack** | Python · Multiprocessing · Shared Memory · OpenCV · Ring Buffer |
| **Architecture** | Zero-Copy IPC via `multiprocessing.shared_memory` · Producer-consumer ring buffer |
| **Performance** | ~40% reduction in data-copy overhead vs queue-based alternatives |
| **Throughput** | Sustained 30 fps processing on commodity hardware |
| **Problem Solved** | GIL elimination for true CPU-bound parallelism in Python CV pipelines |
| **Repository** | [github.com/awaisarif18/LuminaFlow](https://github.com/awaisarif18/LuminaFlow) |

</div>

LuminaFlow exists because Python's GIL makes true parallelism impossible for CPU-bound workloads in a single process. The standard solution — using `multiprocessing` with `Queue` — introduces serialisation overhead that negates much of the benefit for large frame data. LuminaFlow instead allocates a shared memory segment accessible by all worker processes with no copying: the producer writes raw frame bytes into a ring buffer slot and signals a worker; the worker reads directly from the same memory address. The result is a framework capable of processing multiple video streams in parallel at sustained real-time frame rates on standard hardware.
